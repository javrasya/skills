# ADR-0014: A failed agent gets a doctor before it returns null, and its dependents wait while it works

## Status

Accepted — 2026-09-26. Extends ADR-0012 and ADR-0013. Amended by #73 to #76 (the mail protocol, handoff and remedy, doctor rounds that build on each other, never-started and blocked patients, escalation and needs you) and by the #67 integration review (a round's first handoff is its only remedy, mail held by its dispatch, a patient's result not held on its doctor). Applies to the **Orca runner only**. The Workflow runner is unchanged. The shared workflow script changes in two lines only, both for the Orca runner (see Consequences).

## Context

Under ADR-0013 an agent that fails is null at once. That happens when its session dies past the continuation cap, its start fails after every retry, or it waits on a human past the blocked limit. The script then carries on without it, and everything built on that agent is lost with it. Often the failure has a cause another agent could name by reading the failed session: a sandbox that refuses a command, a wrong assumption repeated in each continuation, a login that expired. A continuation carries the same session on with the same blind spot. A restart repeats it.

Orca workers are real sessions with transcripts, a journal names every line of their life, and the runner log holds what the operator saw. So a second agent can read all of that and say what went wrong, while the first is kept as it stands (ADR-0012).

The question is what the script sees while that happens. There were three options:

- **Return null now and repair later.** The script's dependents would already have moved on, so a repair would have nothing to feed into.
- **Throw from `agent()`.** This breaks the promise both runners make to the shared script: `agent()` resolves to a value or null.
- **Keep the call pending.** The script waits on the patient exactly as it waits on any long agent.

## Decision

**A failed agent is a patient, and the runner starts a doctor for it before its `agent()` returns null.** Three failures make a patient: a session dead past its continuation cap, an agent blocked on a human past the blocked limit, and a start whose retries are all spent.

- **The patient's promise stays pending.** Nothing is journaled as `failed` for it yet. A `doctor` line records the round instead. Whatever awaits the patient waits. Every agent that does not depend on it carries on, since the script's own `parallel` and `await` structure decides dependency, not the runner.
- **The patient frees its live slot** before its doctor starts. A doctor needs a slot too, and a patient holding one while it waits on its own doctor would starve the run, or deadlock it at a cap of one. A remedy is applied only once the patient holds a live slot again, by its own supervision, so a live worker is always a watched one inside the cap.
- **The doctor is an agent like any other.** It is a supervised Orca worker started through the same lifecycle, with the same journal, live cap, start retries and liveness. Its worktree is `<runId>-<n>`, named from the run's next agent number, and it is created with Orca's setup hook skipped (`--setup skip`), so no setup output, dirty tree or slow create can fail the doctor itself. It is titled `[<patient's phase>] recover -> <patient label>`, and it runs on the `recover` row of the template's role table. Its nudges and continuation prompts are its own: they tell it to report over Orca mail, never to run a submit command it does not have.
- **The doctor changes nothing.** Its prompt hands it the patient's title, prompt, failure reason, journal entries, runner log lines, transcript path, its worktree path if it has one, which round it is of three, and each earlier round's note and how that round ended. Its only output is a note. When a human is needed, it states the situation and what the human must do or decide, without questioning them.
- **A doctor reports over the Run mailbox.** It has no submit command. The runner reads the mailbox from its own terminal while a doctor is out. A `handoff` carries the note. An `escalation` says a human is needed. A `worker_done --outcome failed` gives up, and any other `worker_done` ends the doctor.
- **Each message is acted on exactly once.** It is journaled as `mail`, with what the runner did, then acted on, and only then acknowledged. Orca delivers a batch again until it is acknowledged, and a resume's `run-use` delivers it again under a new id. A message id already journaled is acknowledged and never acted on again. A message is acted on only for the doctor whose dispatch sent it. One read before that doctor's box has claimed its dispatch is **held by its dispatch**: journaled `pending` with the whole message, acknowledged, and applied in order once the box claims it. It is never consumed with nothing done. A resume holds every pending message again.
- **A round's first handoff is its remedy, and its only one.** A later `handoff` or `escalation` from that doctor is journaled with `action: none` and acts on nothing. Only its `worker_done`, or its own lifecycle, ends it. The doctor's prompt says so. A doctor goes back and forth with the operator by escalating as often as it needs *before* its note. After the note, the patient carries on with it.
- **A doctor that escalates needs you** until its next `handoff`, `escalation` or `worker_done`. It is never nudged or continued for idling or stillness, and the blocked limit does not count against it, so it waits for as long as the human takes. The runner logs `NEEDS YOU` with the tab to answer it in, and the run view shows it.
- **The remedy carries the patient on under its original call.** A patient with a session has that session continued, in its own worktree, in its own tab or a new one once that tab is gone, with the note in its continuation prompt (`how: continue`). A patient whose worker never started has no session, so its start is retried with the note appended to its worker's prompt (`how: restart`). Either way its journal key stays the original call's, and a resume replays its result. A remedy starts a fresh count of continuations, and a restart a fresh set of start retries, so a later round never begins with none left.
- **The patient's result is not held on its doctor.** A patient's `agent()` resolves as soon as its own result is in. A doctor still out after its handoff goes on in the background, watched as any agent is, and the runner waits for every such doctor to end before it writes `summary.json`.
- **At most three rounds, and a doctor is never doctored.** A doctor that ends without a remedy spends its round. That covers a doctor that gives up, one whose worker settles with no handoff, and one that fails itself after its own start retries and continuations. A remedied patient that fails again starts the next round, whose doctor sees that note failed. After the third round the patient's call returns null, and it is failed and kept, as before.
- **A resume goes on with a held patient's open round.** A live doctor is taken up, never a second one started. A handoff journaled but not yet applied is applied once. A doctor that never launched is started afresh in the same round.

## Consequences

- **Dependents can wait a long time.** The cost is that a failure no doctor can mend holds its dependents up for three doctor rounds before they learn it is null. A doctor that needs you holds them up until the human answers. The run as a whole never stalls on it, because independent work goes on. And a result that comes late is better than a null at once for work that is built on it.
- **A note cannot be taken back.** Once a doctor has handed off, nothing more it says changes the patient. A note that was wrong shows up as the patient failing again, and the next round's doctor is told so.
- **The doctor is visible like any agent.** It has its own tab, worktree, journal lines and `<runId>-<n>`, so the operator can watch it, and reclaim finds it. The journal links it to its patient: the patient's `doctor` line names the doctor's n, the fold gives each patient its `doctors`, `round` and `rounds`, and it gives each doctor its `patient`. A doctor that gave up is a failed row, never a done one.
- **A doctor's failure is not the run's failure.** Its lines carry `key: null`, since it is no `agent()` call. Its `failed` line names its patient and is not counted towards a partial run, and its worktree is never retained: it changes nothing, so it holds no work. Only the patient's final `failed` counts.
- **The runner has to read the role table, and the shared script changes for it.** A doctor is started by the runner, not by an `agent()` call with a role row spread into it. So `workflow.template.js` gains a `recover` row in `ROLES`, and hands the table over with `if (ON_ORCA) meta.roles = ROLES`. The runner checks the row at the first `agent()`, before any worker. The Workflow runner is unaffected: the guard sets nothing unless `RUNNER` is `orca`, and no `agent()` call spreads the `recover` row, so under the Workflow runner it is never read. `scripts/simulate-implement-spec-workflow.mjs` covers this: it drives the rendered template with stubbed `agent()` calls under each runner, and checks that the script rendered for each differs only in `RUNNER`.
- **The doctor's rules live in one module.** `orca/doctor.mjs` holds the doctor's prompts, the Run mailbox, what the runner does with each message, the rounds and their remedy, and the journal fold's reading of them. The runner and the fold therefore share one set of round and mail rules.
